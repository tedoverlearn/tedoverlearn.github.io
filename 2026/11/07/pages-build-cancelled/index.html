部署脚本说 OK，网站还是 404

发表于2026-11-07|更新于2026-11-10|AI 实践
|浏览量:

昨天晚上十一点，我在两个地方各看到一次成功：本地 hexo generate 生成了 98 个文件，deploy.bat 的最后一行打印着 [deploy] OK - pushed to GitHub，退出码 0。然后在浏览器里打开文章链接，404。

三个东西容易混成一个：本地构建成功、代码推上去、网站真的更新了。前两个我只能证明「送到」，第三个要等 GitHub 那边重新发布。

一、先确认文件到底在不在仓库

第一反应是推送没生效。这种时候最省事的不是重跑一遍，是直接问仓库要文件。

返回里有一条 index.html，size 是 29127，sha 是 1aef201b19269c42679f4e8a32ae1d73c4d3ef88。文件在 main 分支上，路径对，大小也在合理区间。

这一步排除了一大类问题：推送失败、分支搞错、路径大小写不对、文件根本没生成。有 sha 有个好处，后面还能用它核对线上那份到底是不是同一个东西。

二、再看构建：三个接口，看三件不同的事

Pages 的发布不是 git push 的一部分，它是仓库上的一次构建。查它有三个入口：

/deployments 看这次部署本身，返回 sha、ref、created_at。我查到的是部署 7603127605，对应提交 ba6f4a3，创建时间 14:57:23Z。

/deployments/{id}/statuses 看部署走到了哪一步。返回里按时间倒序三条：waiting、queued、in_progress，最后一条停在 14:57:27Z，之后再没有新状态。也就是说，这次部署开始了，但一直没等到结束。

/actions/runs 看真正跑的那次工作流。这里才有关键字段：conclusion。我查到的是 cancelled——不是失败，是取消。

失败和取消是两件事。失败说明构建过程中有东西报错，去看日志能找到原因；取消说明有人或什么东西把它停掉了，日志里往往什么都不会写。我一开始按失败的思路排查，翻了半天没进展，就是没注意这个区别。

三、时间线一对，原因就出来了

把四次事件按时间排开：

时间（北京） 事件
22:56:38 推送 ba6f4a3，deploy.bat 打印 OK，部署创建，状态进入 in_progress
23:00:09 每晚 23:00 的计划任务照常跑了一遍，又推了一个提交 a6517c3，触发新的构建
23:01:16 第一次构建（run 44）结论变成 cancelled
23:07:19 我补推一个空提交 362ec4d，想重新触发
23:08:08 第二次构建（run 45）同样变成 cancelled
23:14:58 第三次构建（run 46）结束，结论 success

两次取消，都发生在新的推送之后一分钟左右。这个规律太整齐了，不太像偶然。合理的解释是：Pages 对同一个站点的构建是串行的，新的提交进来会把还没跑完的那次取消掉。

这是我的推断，不是我从文档里抄的结论。GitHub 的文档写了这些接口的字段和状态值，但没写「新提交会取消旧构建」。所以这里我只能说现象吻合，机制是我的解释。

代价也很实在：我那次 22:56 的推送本来会成功，被 23:00 的例行任务顶掉了；而例行任务本身什么内容都没改（只推了一个空提交），它唯一的作用就是把前一次构建挤掉。

四、怎么让它重新跑起来

最直接的办法是再推一个提交。我的做法是不改任何文件，直接推一个空提交：

--allow-empty 的意思是不产生内容变更，但提交对象是新的，Pages 就会把它当成一次新构建。这次跑完了，7 分 33 秒，success，链接变 200。

这个办法能用，但不好看：提交历史里多了一条什么都没干的记录。更干净的做法是在仓库的 Actions 页面里手动 re-run 那条 pages build and deployment，我在本地没有 token，查不到也无权重跑，所以选了空提交这条笨路。

五、更该改的是流程

这次真正暴露的不是某一个 bug，是我把「推送成功」当成了「发布成功」。修法有三层，从便宜到贵：

第一层，别在短时间内连推两次。我的部署是 23:00 固定跑，文章发布又常在 22:50 前后，两者天然撞车。生成文章后如果确实要立刻推送，就把当天的 23:00 任务跳过；或者干脆让 23:00 那一次什么都不做。

第二层，推送后等一会儿再核对线上地址。等多久没有固定值，这次是 7 分 33 秒，前几天是 60 到 90 秒。可以写成轮询：每分钟请求一次文章 URL，拿到 200 就停，超过 10 分钟就告警。

第三层，把核对写进部署脚本的返回值。现在的 deploy.bat 是用 findstr 去匹配 Deploy done 这行输出、以此判断推送成功，这只覆盖了 git 那一半。如果再加一步：curl 一下首页，非 200 就把退出码改成非 0，那日志里那个 OK 才真能代表「网站变了」。

第三层我还没实现。今天这篇只做到第一层和第二层，脚本还是原来那个。

六、三处没解决的

第一，没有 token 的情况下查不到构建日志。上面三个接口是公开的，能看到状态和结论，但看不了构建过程里发生了什么，也无权重跑。要补这块得申请一个有 repo 权限的 token，我暂时不想往这个项目里加凭据。

第二，空提交会污染历史。今天补的那条 362ec4d 永远留在仓库里，什么都没改。偶尔一次可以接受，如果变成常规操作，提交历史就没法看了。

第三，CDN 缓存会让判断变复杂。我昨晚有两次查到的还是 404，但半小时后再查就正常了。到底是构建没好，还是缓存没刷新，从外面看不出来。这也是为什么我倾向等足十分钟再下结论。

最后

部署这件事，脚本能证明的只有它做过什么，证明不了网站上现在是什么。我写这句不是想显得谨慎，是昨晚真的在这上面判断错了二十分钟——两个人都在说 OK，而链接是 404。

现在我的检查顺序固定成三步：仓库里有没有这个文件、构建的结论是什么、线上地址返回什么。三步都过了，才叫发布完成。
