个人仓库的 GitHub Issue，哪些信息值得单独设字段

发表于2026-11-13|更新于2026-11-13|AI 实践
|浏览量:

写在前面

个人仓库的待办一多，最先乱的往往是 Issue 标题。为了在列表里分清问题和待办，标题前会加「Bug」或「任务」。为了看出先后，又补上「紧急」或「本周」。读到最后才知道这条 Issue 要解决什么。GitHub 在 11 月 11 日宣布，个人账户拥有的仓库也可以使用 Issue 类型和字段。这个变化值得留意，因为原来写在标题里的信息，现在有些可以放到更容易筛选的位置。

下面以个人博客的维护工作为例，设计一套可以试用的配置。示例 Issue 和字段值都是为了说明做法而设定，具体界面以账户里实际显示为准。

类型回答「这是什么」，优先级回答「先做哪件」

GitHub 公告列出的默认类型是 Bug、Task 和 Feature。拿博客来说，假设首页能打开、文章链接却返回 404，可以建一条 Bug，标题写「文章页链接返回 404」。为下一篇文章整理参考资料，属于 Task。想在博客加一个按月份浏览的页面，可以列为 Feature。这样扫一眼类型就知道要修、要做，还是要新增。

同一条 Bug 的优先级却可能变化。只有一篇旧文的链接失效，和首页所有文章都点不开，处理顺序当然不同。把优先级放到单独的字段里，情况变了只需要改字段。GitHub 文档还说明，字段值的变更会记录在 Issue 时间线中。接手一条旧问题时，如果发现优先级提高，可以顺着记录找到变化发生的时间，再看同期讨论里有没有补充证据。

给自己用时，可以先只配置类型和优先级两个维度。如果一项信息既不会影响处理顺序，也不会用于后续筛选，通常在正文里交代一句就够了。GitHub 提供了文本、日期、单选等字段类型，实际要加哪一种，可以等到同一个整理动作反复出现再决定。

正文留给复现步骤和完成条件

以文章页返回 404 为例，标题只写现象。正文放具体的复现步骤，包括从哪个页面点进来、期望看到什么、实际出现什么。对于一次准备工作，则写清交付物。比如资料整理做完时，应能打开哪些公开页面，以及每个页面支撑哪个事实。这个说明比只填一个截止日期更能帮助自己判断任务是否完成。

字段的价值在于后续找得到。按 GitHub 文档，可以在仓库的 Issues 页面按字段值筛选，例如用 field.priority:high 查找高优先级事项。如果某些信息只对某类 Issue 有用，还可以把字段固定到对应类型。这样创建该类型的 Issue 时，对应字段会出现。对只有一个人维护的博客而言，先用少数固定字段，等实际发现遗漏，再调整更省心。

公开仓库还要区分哪些信息适合公开。GitHub 的说明是，设为 Restricted 的字段，在个人账户拥有的仓库里只对所有者和至少有读取权限的协作者可见。文章草稿的私人素材、账号凭据和含个人信息的原始记录，仍应留在适当的位置。尤其是问题描述和截图，发出前应单独检查一遍。

从新开的几条 Issue 开始

如果要把这套配置用到个人博客，我会先挑接下来实际要处理的三条 Issue，各写一句能独立读懂的标题，再用类型和优先级归类。过一周试着回答两个问题。第一，能否在一分钟内找到目前优先处理的故障。第二，能否在下次打开 Issue 时仅凭正文恢复工作。如果前一个问题答不上来，就检查字段值是否统一。如果后一个问题答不上来，就补正文里的复现步骤或完成条件。这样能看出该改的是记录方式，还是字段本身。

这套做法能否节省时间，取决于我以后是否真的会用这些字段筛选。只有零星几条 Issue 时，简单的标题和清楚的正文可能已经够用。等待办多到需要定期回顾，结构化字段才更容易体现价值。
