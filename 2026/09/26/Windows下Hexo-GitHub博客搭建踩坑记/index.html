写在前面

过去的法律学习更多围绕法条、案例和理论展开，但随着 AI 工具进入法律检索、合同审查、法律服务等领域，我逐渐意识到，未来法律人才不仅需要具备法律思维，也需要具备一定的技术理解能力。

作为一个法学本科大三学生，我最近开始自学 AI 应用开发。为了记录学习过程、给简历增加一个可以展示的实体项目，我决定搭建一个个人技术博客。

然而，从选择方案到最终上线，我几乎把新手能踩的坑全踩了一遍。这篇文章不是为了写一篇完美的教程，而是为了如实记录我作为纯小白，在 Windows 系统下从零搭建 Hexo 博客的真实过程与解决方案。

如果你也是零基础，希望我的经历能帮你少走一点弯路。

我的环境

  • Windows 11
  • Node.js xx
  • npm xx
  • Hexo xx
  • Git xx
  • PowerShell xx
  • GitHub Pages

第一个坑：目录权限与路径空格

最初我把博客项目放在 D:\ai playground 目录下。结果第一步就惨遭 Windows 权限教育：
PS D:\ai playground2> mkdir D:\ai playground
mkdir : 找不到接受实际参数“playground”的位置形式参数。

原因：路径名带空格，在 PowerShell 里被解析成了两个参数。
加上引号后，又提示 EPERM: operation not permitted——当前用户对这个文件夹没有写权限。

解决：不要和 Windows 权限系统死磕。直接换到用户根目录 C:\Users\你的用户名\aiblog 下，问题迎刃而解。博客源码放在哪里，完全不影响以后的部署。

教训：不建议把项目放在路径复杂、包含特殊字符或权限管理复杂的位置。

第二个坑：PowerShell 的“古老”限制

在跟着教程走的时候，教程里经常用 hexo clean && hexo g && hexo s。
Windows PowerShell 5.x 不支持类似 Linux Shell 和新版 PowerShell 7 中的 && 链式执行语法:
标记“&&”不是此版本中的有效语句分隔符。

解决：在旧版 PowerShell 里，用分号 ; 代替 &&，或者逐条执行。如果非要使用 &&，需要安装 PowerShell 7。

第三个坑：终端命令 vs 文件内容

作为一个新手，我一度把“写在配置文件里的内容”和“在终端里执行的命令”搞混了。

比如我直接把 theme: landscape 敲进终端，导致：
theme: : 无法将“theme:”项识别为 cmdlet…

同样，我甚至把 Markdown 格式的标题（--- 和 title:）一起粘贴到终端里运行，PowerShell 也完全不给面子，直接报了一串奇怪的“一元运算符”错误。

教训：带冒号（key: value）的 YAML 配置，是写在 .yml 文件里的；hexo g、npm install 这类才是敲在终端里的。

第四个坑：YAML 语法的重复键

在配置 Hexo 部署地址时，我按照教程添加了：

但我没注意到文件底下原来就有一个默认的 type: ‘’，导致 YAML 解析器报错：

YAMLException: duplicated mapping key (107:3)
解决：合并配置，删除旧的空 type，只保留一个 type: git。

第五个坑：GitHub 连不上与 SSH 救场

这是整个过程中最折磨人的环节。由于本地网络环境限制，git clone 和 git push 经常在 HTTPS 协议下直接卡死，或者报 Connection was reset。

我尝试了开启代理工具（假设本地端口为 你的代理端口，例如 7890）并配置 Git 代理：

</>powershell
git config –global http.proxy http://127.0.0.1:你的代理端口

奇怪的是，浏览器能访问 GitHub，Test-NetConnection 也显示 443 端口通，但 Git 依然卡死。

最终解法：彻底放弃 HTTPS 方式，转用 SSH 协议。

生成 SSH 密钥：ssh-keygen -t ed25519 -C “你的邮箱@example.com”

复制公钥 id_ed25519.pub 到 GitHub 的 SSH Keys 中。

修改 Hexo 配置，把 repo 换成：git@github.com:你的GitHub用户名/你的GitHub用户名.github.io.git

收获：SSH 方式走的是 22 端口，在我的网络环境下，SSH 方式比 HTTPS 推送更加稳定。如果遇到 HTTPS 连接异常，可以尝试切换 SSH 协议。

第六个坑：Git 不知道“我是谁”

配好了 SSH，满心欢喜执行 hexo d，结果又报错：

Author identity unknown
*** Please tell me who you are.
解决：部署前，务必告诉 Git 你的身份（换成你注册 GitHub 的邮箱）：

powershell
git config –global user.name “你的GitHub用户名”
git config –global user.email “你的邮箱@example.com”
最后的成功与反思
当你看到终端最后出现：

INFO Deploy done: git
并在浏览器里成功打开自己的博客时，那种成就感是非常真实的。

作为一个法学背景、刚接触 AI 和代码的新手，这次经历让我学到的不仅仅是“怎么建一个网站”，更是一种工程化解决问题的思维:

看报错信息：Git、PowerShell、Node.js 的报错其实非常清晰，里面会直接告诉你哪一行出了问题。

分而治之：网络问题、权限问题、语法问题，虽然看起来都是一团乱麻，但要拆开，逐个击破。

善用工具：遇到不懂的，我会直接问 Cursor 里的 AI 助手，或者把错误日志丢给 AI 帮我解读。

这次经历也让我重新理解法律学习与技术学习的共同点。无论是分析一个法律案件，还是排查一个程序错误，本质上都是面对复杂问题，通过信息检索、规则理解和逻辑拆解寻找解决方案。

下一步，这个博客会成为我记录法律 AI 项目（比如合同审查工具、民法典问答助手）的基地。技术之路才刚刚开始，与大家共勉。
