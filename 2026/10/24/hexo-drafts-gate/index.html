给博客加一道审核闸门：用 Hexo 的 _drafts 把「自动写」和「自动发」拆开

写在前面

这个博客从搭好到现在，更新一直不稳定。不是因为没东西写，而是因为写东西这件事被”要写得好”卡住了：法条要核对、案例要查证、技术细节要自己跑过才敢写。结果就是想法攒了一堆，发布记录停在几个月前。

后来我想换一个思路：把”写”这一步交给流程，把”发”这一步留给自己。每天机器固定产出一篇草稿，我只做审核。这样更新频率的问题解决了，内容准确性的责任也没有被交出去。

这篇记录一下具体怎么做的，重点是为什么用 Hexo 自带的东西就够，而不是另搭一套系统。

问题不在”写”，在”发”

一开始的想法很直接：写个脚本，接上模型 API，每天生成一篇文章，丢进 source/_posts，然后部署。

想了两分钟就发现这条路走不通。问题不在模型能不能写出一千字，而在于它写出来的东西没人看过就直接上线了。对一个写法律内容的博客来说，这不是效率问题，是风险问题。一个条号写错、一个案例张冠李戴、”涉嫌”被写成”构成”，读者不会因为你更新勤快就原谅你。

所以我真正要设计的不是”生成流程”，而是”谁敢按下发布按钮“。

答案很简单：机器负责产出候选，人负责按下按钮。

Hexo 本来就留了这个位置

这是我最开始没想到的：Hexo 里本来就有草稿这个概念，不需要自己造状态机，也不需要加数据库。

按官方文档的说法，Hexo 有三种默认 layout：post、page、draft，它们分别写到不同的目录：

Layout 路径
post source/_posts
page source
draft source/_drafts

关键在下一句：草稿默认不会被渲染。要渲染草稿，得在命令里加 --draft 参数，或者在 _config.yml 里把 render_drafts 打开。

我的目录约定

真正动起手来，我给自己定了两个约定。

第一个：所有跟自动更新有关的东西都放在 _auto-blog/ 下。

这个目录不在 source/ 下面，Hexo 生成站点时不会碰它，所以配置和日志不会被打包进公开的静态文件。这一点值得单独说：把配置放在 source/ 里，是很容易犯的错。

第二个：草稿文件名用 YYYY-MM-DD-slug.md。

日期是幂等键。每天任务开始的第一件事，就是看 source/_drafts/ 里有没有今天日期的文件、state.yml 里今天的运行状态是不是已经成功。有就跳过。这样即使定时任务被触发两次，也不会在同一天产出两篇。

每天那一次是怎么跑的

流程本身不复杂，写进 daily-prompt.md 之后大概是这样：

  1. 先做幂等和窗口检查。今天已经成功过就跳过；当前时间不在设定窗口内就跳过。深夜被唤醒绝不补发——这条是硬规则，人半夜写的稿子质量最差，机器也一样。
  2. 选题。AI 实践 50%、法律思考 25%、热点评论 25%，但比例是参考不是 KPI。当天没有可靠来源的热点，就不追，转去写技术或法律专题。
  3. 检索。搜索和抓取都有次数上限，宁可写短一点，也不无限查。
  4. 写。一千到两千字，文末列参考资料。
  5. 质检。九项清单，过不了就留在草稿里标记”需要人看”，不发布。
  6. 落盘 + 记日志。日志记计划时间、实际时间、标题、分类、来源数、质检结果、模型轮次、估算费用。
  7. 排明天的任务。这一条容易漏：如果每天的任务是靠”上一次任务给下一次排期”，那么今天失败了，明天就断了。

第 7 条是我觉得最值得写下来的经验。定时任务不是配一次就完事，它需要自己续命，而且续命失败必须报警，不能静静断掉。

审核的时候我只看四件事

流程再复杂，人这一环最后就四个动作：

  1. 点开链接。每一条参考资料都是不是真的存在、内容是不是对得上。
  2. 核条号。法律文章里出现的每一个”第 X 条”都要回原文对一遍，包括是不是现行有效版本。
  3. 看措辞。有没有把”涉嫌”写成”构成”，有没有把个人观点写成司法结论。
  4. 查有没有编造我。有没有写我没做过的项目、没跑过的命令、没得到过的结果。

第四条其实是最容易出问题、也最难自查的。模型很擅长把”这件事应该这样做”写成”我是这样做的”。所以我在流程里加了一条硬约束：没有实际运行验证过的方案，只能写成方案或设想。

还没解决的问题

这套东西不完美，有三件事我想清楚了但没解决：

第一，定时依赖客户端在运行。 定时任务是排在我这台机器的客户端里的，不是云上的 cron。机器关着、客户端没开，当天的任务就不会执行。我的选择是：错过就错过，记录失败，不补发。宁可少一篇，也不要为了”完成任务”在凌晨两点赶一篇低质量的稿子出来。

第二，构建和发布还没做到自动。 我当前的终端环境对这个博客目录没有写权限，跑不起 hexo generate，所以”草稿能不能正常构建”这一步暂时还得我手动验证。在权限问题解决之前，把自动发布打开是不负责任的——没构建过的站点推上去，坏的是线上。

第三，质检是清单不是证明。 九项清单能挡住大部分明显问题，但挡不住”看起来对、其实错”的法律分析。所以自动检查通过的稿子，我仍然会自己读一遍再发。自动化的价值是把”从零写一篇”变成”审一篇”，不是把责任转移出去。

小结

做完这件事，我最大的收获不是学会配定时任务，而是想清楚了一个边界：自动化应该放在”生产”这一侧，”发布”这一侧要留给人。

生成可以快、可以多、可以试错；发布必须慢、必须少、必须有个人签字。这两件事拆开之后，每天更新的压力就变成了每天审一篇的十分钟，而不是每天从零写一篇的两小时。

至于内容质量——那是另一个问题，流程解决不了，只能靠写和读。但至少现在，流程不会再挡住我开始写了。
