hexo 不是 exe，是 npm 装的命令行包。cmd 里敲 hexo，命中的是 npm 生成的 hexo.cmd 包装脚本，最后一行大概长这样：

二、退出码不能当成功判据

第二版加上了判错：if errorlevel 1 goto :fail。结果第一次就报”部署失败”，可 GitHub 上明明多了一次提交。

原因不止一个。hexo deploy 内部调 git push，推送成功之后仍可能返回非 0；另外，git 的传输子进程在受限环境里会被拦，报 cannot create standard input pipe for ssh，这也是非 0。两个方向都不准：成功不保证返回 0，返回 0 也不保证推上去了。

最后的判据换成了字符串：把第三步的输出重定向到临时文件，再找 Deploy done。

findstr 找到返回 0，找不到返回 1，这个是可靠的。听起来很土，但它把”到底推上去没有”绑到了 hexo 自己打印的成功标记上，比一个语义含糊的退出码可信。

三、cmd 读 .bat 用的是 OEM 代码页

有一版往脚本里写了中文注释和中文 echo。前台跑没事，计划任务跑出来的日志里全是乱码。中文 Windows 的控制台代码页默认是 936，chcp 的文档里 936 对应”Chinese”。文件按 UTF-8 存，cmd 按 GBK 读，中文部分就被错误解释，注释里的字节甚至可能吃掉后面的引号或括号，导致整段语法失效。

没有动系统代码页——那会影响别的程序。改法是把 .bat 写成纯 ASCII：注释用英文，错误提示用英文，中文只出现在文章和日志里。代价是脚本不好读，收益是它在任何代码页下行为一致。

五、没改动的部署，也会产生一次提交

前一晚 23:00 那次运行，当天的文章在 22:50 已经推过了，理论上这次应该无事可做。日志里是：

28 个文件”变了”，但内容一个字没改。上面还有一行提示：warning: in the working copy of 'tags/Git/index.html', LF will be replaced by CRLF the next time Git touches it。

这是 core.autocrlf 的老问题：检出时把 LF 换成 CRLF 写进工作区，提交时再换回 LF。Hexo 每次 generate 都会重写这些 HTML，写出来是 LF，而工作区里那份被 Git 记成了 CRLF，于是每次都被算成修改。

三种改法：

  1. 在 .deploy_git 里把 core.autocrlf 设成 false；
  2. 仓库根放一个 .gitattributes，写 * text=auto eol=lf；
  3. 部署前先 git -C .deploy_git checkout -- . 把工作区归位。

这条暂时没改，只当噪声处理——不影响上线。但如果以后要按提交记录回溯”哪天发了哪一篇”，这些空提交会让历史变脏，早晚要收拾。

收尾

这五处里没有一处是 Hexo 的 bug。shim 丢参是 npm 包装脚本和环境的事，退出码不可靠是子进程语义的事，代码页和括号块是 cmd 的事，CRLF 是 Git 的事。它们共同的形状是：脚本在”谁调用它、环境长什么样”这件事上假设了太多。

所以现在 deploy.bat 里每一段只做一件事，出错就 goto 一个标签，退出码 0/1/2/3 分别对应 clean、generate、deploy 三个阶段失败；而判断成功的依据是一个写在日志里的字符串，不是那个谁都不太信得过的返回值。

写脚本的时候容易被”它能跑”骗过去。真正要问的是：它能不能区分”成功””失败””什么都没发生”这三种情况。第三种的坑最深，因为它的返回码和成功长得一模一样。
